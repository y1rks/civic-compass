# 設計上の制約

**破ると設計が壊れる約束事**をまとめたもの。いずれも議論の末に決まったことで、
思いつきで変えてよいものは1つもない。

データが何であるかは `docs/data-reference.md`、マッチ計算の実装は
`docs/implementing-match-api.md` にある。ここは**なぜそうなっているか**を扱う。

---

## 1. 何を作っているか

ニュースアプリ。ユーザーが記事に「関心の有無」と「意見」を登録すると、
**考え方の近い政治家・政党**を提示する。

| ID | 名前 | 実行タイミング |
|---|---|---|
| **A** | 議員プロファイル構築バッチ | 事前（Cron） |
| **B** | 意見保存直後のポップアップ API | リクエスト時 |
| **C** | ユーザーページのマッチ度 API | リクエスト時 |

### A のパイプライン

```
国会会議録API (https://kokkai.ndl.go.jp/api/speech)
  ↓ 収集                                    scripts/kokkai/collect.mjs
raw speeches
  ↓ ① 機械的フィルタ（200字未満・定型文を除外）  scripts/kokkai/preprocess.mjs
  ↓ ② LLM で segment 分割（トピック境界で切る）
  ↓ ③ LLM で抽出          ← 分割と抽出は必ず別呼び出し
【1】utterances (D1)
  ↓ ④ 集計（LLM 不要・数秒）                  scripts/kokkai/build-profiles.mjs
【2】profile / evidence / cellidx (KV)
```

`scripts/README.md` と `scripts/kokkai/README.md` に各工程の詳細がある。

## 2. 中核の設計思想 —— 政策の賛否ではなく「正当化の論理」でマッチさせる

既存のボートマッチ（政策ごとに賛否を選ばせる方式）を避けるのが目的。
政策マッチだと「政策は合うが思想は合わない」が起きるため。

同じ「選択的夫婦別姓に賛成」でも、

- 個人の自己決定（`liberty_autonomy`）から言う人
- ジェンダー平等・ケア（`care_harm`）から言う人
- 事務コストの非効率（`efficiency_utility`）から言う人

は別の思想。**この差を捉えることがプロダクトの中核価値**。

マッチングは **`frame × target × role` のセル**で行う。
語彙の定義は `docs/data-reference.md`「中核となる概念」、
実体は `shared/src/vocabulary.ts`（唯一の正）。

## 3. 禁止事項

### ❌ セルキーから `role` を落とす

`beneficiary` と `threat` を畳むと、正反対の思想が同一視される。

```
議員X: care_harm × 外国人・移民 × beneficiary（支援すべき）
議員Y: care_harm × 外国人・移民 × threat      （治安上の懸念）
```

セルキーは必ず `frame | target | role` の3要素。

### ❌ フレーム単独で議員の傾向を持つ

政治家単位で frame の向きは決まらない（対象によって変わる）。
`liberty_autonomy` だけだと「経済的自由を語る議員」と「個人の自由を語る議員」が
混同される。必ず `frame × target` のセル単位で持つ。

### ❌ トピック（`topic_id`）を持つ

不採用が決定済み。文脈情報は `target` で代替する。

### ❌ LLM に価値軸スコア（-1〜+1 の連続値）を直接出させる

出させるのは離散ラベル（`frame` / `stance` / `targets`）と `intensity` まで。
スコアは後段の集計で算出する。連続値は原文と突き合わせた検証ができない。

### ❌ 推論でタグを付ける

原文に言及がない価値にタグを付けない。
「この立場を取る人は通常この価値も重視するはずだ」は**推論であって観測ではない**。

`evidence_span` を示せないタグは付けない。この規律を構造的に強制するために
必須フィールドにしてある。実装は `scripts/kokkai/align.mjs` で、
LLM が返した引用を原文と照合し、**見つからないタグは破棄する**。

`evidence_span` を LLM に数えさせないのも同じ理由。必ずずれるうえ、
コード側で `indexOf` すれば原文にない引用を機械的に検出できる。

### ❌ LLM に政治家の主張を記憶から語らせる

理由文・引用文は**必ず【1】に保存した原文から**。
政治テーマでの捏造は致命傷。B / C の理由文はテンプレート
（フレーム名の日本語化）で生成し、**LLM に作文させない**。

### ❌ 【1】utterances を書き換える / 経由せずに【2】を直接書く

【2】の集計式は必ず変わる。【1】が残っていれば LLM 再実行なしで作り直せる。
utterances は**追記のみ**。

### ❌ 分割と抽出を1回の LLM 呼び出しでやる

境界判定と抽出が同時に走ると品質が落ちる。必ず分ける。
手作業のパイロット（`scripts/kokkai/apply-split.mjs` → 抽出）でも工程を分けている。

## 3.5 抽出モデルの選定 —— 引用一致率が最重要

パイロット58件を Opus5 の手動抽出と突き合わせて5モデルを比較し、
**`@cf/zai-org/glm-5.2`（Cloudflare Workers AI）** に決めた。
比較スクリプトは `scripts/kokkai/workers-ai-bench.mjs`
（`--all --verbose` で全件・詳細比較）、生の結果は `data/pilot/ai-bench*.json`。

| モデル | 引用一致 | frame+stance 再現 | override | 速度 |
|---|---:|---:|---:|---:|
| **@cf/zai-org/glm-5.2** | **95%** | **81%** | 14件（Opus5:12） | 25秒/件 |
| @cf/moonshotai/kimi-k2.6 | — | 57% | — | 82秒/件 |
| @cf/nvidia/nemotron-3-120b-a12b | 100% | 64% | **0件** | 48秒/件 |
| @cf/openai/gpt-oss-120b | 94% | 64% | 1件 | 26秒/件 |
| @cf/meta/llama-3.3-70b-instruct-fp8-fast | **0%** | — | — | 24秒/件 |

**引用一致率が最重要**なのは「推論でタグを付けない」の帰結。`evidence_text` が
原文と一致しないタグは `align.mjs` が破棄するので、日本語生成が崩壊して
一致率0%の llama-3.3-70b は**全タグが消えて使い物にならない**。

nemotron は引用一致100%だが `override` を1件も拾えず、
天畠大輔の `liberty_autonomy` が負の score になる現象を再現できなかった。
`override` は出現率が低いぶん情報量が大きいので、拾えないモデルは採れない。

プロンプト改善（v1 → v2）で分布相関の平均が +0.73 → +0.81 に上がった。
弱点は2つで、**否定的文脈の override を落とす**ことと
**暗黙の `sovereignty` を落とす**こと。`scripts/kokkai/prompts/extract.md` の例4と
「出力する前に確認すること」がその対策にあたる。

## 4. ユーザー側の入力（記事の設問）

記事ごとに**争点を設問化**し、`frame × target × role` を1つ固定して
`uphold` / `override` / `neutral` の3択を単一選択で答えてもらう。
テーブルは `article_questions` / `article_question_options`。

### ❌ `stance` を UI コントロール（賛成／反対ボタン）にする

`uphold` は「その価値を根拠として持ち出した」、`override` は
「その価値を優先順位で下に置いた」という**言語行為の分類**であって、
政策への賛否ではない。一般の利用者は必ず「賛否」と解釈する。

```
記事「夫婦別姓の法案」に「反対」
  → liberty_autonomy を override した、とは限らない
  → 実際は loyalty_community × 家族 を uphold しただけ、が普通
```

`stance` は必ず選択肢の**文面**に埋め込み、利用者には
「どの言い分が自分の考えに近いか」だけを選ばせる。

### ❌ `stance: neutral` を cells に入れる

`score: 0` のセルとして集計すると、議員側の `score` が +0.9 台に張り付いている
ため `agree = 1 - |0 - 0.9| / 2 = 0.55` が確定する。これが全議員に均等に加算され、
**「全部どちらとも言えない」と答えた利用者が最も高いマッチ度を得る**
（実測で確認済み）。

議員側の `stance: neutral` は全体の 0.2%（15,750件中25件）しかない。
片側だけ neutral が多いとスケールが合わない。

`neutral` は回答レコードには残し、cells には入れない（＝「語らなかった」扱い）。

### ❌ `interest = 0`（関心がない）の回答を cells に入れる

寄与 `w` が 0 でも、`share` はベイズ平滑化されているので 0 になりません。実測で
「関心がない」セルが share 0.232、本当に重視しているセルが 0.268 と、ほぼ並びます。
しかも分母に入るので、そのセルを持たない議員が減点されます。集計前に落とすこと。

「関心がない」は捨てるのではなく、**「まだ答えていない」とは別のバケツ**に入れて
マッチに使います（`DECLINED_WEIGHT` > `SILENT_WEIGHT`）。明示的に降りたことは、
出会っていないことより情報量が大きいためです。詳細は `docs/implementing-match-api.md`。

### ❌ 逆の `role` で語っていることを、ただの「不一致」として扱う

同じ `frame × target` を逆の role で強く語っている相手は**減点する**
（`OPPOSITE_ROLE_WEIGHT`）。「外国人・移民を守る対象として語る」と
「脅威として名指す」は、一致しないだけでなく**対立**だから。

閾値（`STRONG_SCORE`）は**ユーザー側と議員側で同じ値**にすること。
外すと、脅威の枠組みを持ち出したうえで**退けた**発言まで減点に数える。

### ❌ 相手が語っていないセルを、ただの「不一致」として捨てる

議員・政党が**一度も語っていない**セルは、`score = -1`（優先順位を下げた）の
仮想セルとみなしてユーザーと突き合わせる（`ABSENCE_WEIGHT`）。

捨てると、**ユーザーの `override` 回答がどの相手にも効かなくなる**。議員側の score は
9割方 +1 に張り付くので、相手が語っていれば `agree = 0`、語っていなければ寄与ゼロ、
のどちらかにしかならない。実測のユーザーで11セル中4セル（分母の36%）が死んでいた。

とくに公約は網羅的に掲げるものなので、**載せていない＝明示的に優先順位を下げた**と読める。

ただし**観測量で割り引くこと**。語っていないセルは観測が少ない相手ほど増えるので、
満額で数えるとデータの薄い相手が有利になる（実測で Σn=306 の議員が4位→2位）。
公約（`manifesto` / `mixed`）だけは量に関わらず満額でよい。

### ❌ 片側だけに補正を掛ける

`override` の稀少性重み `k` と `share` のベイズ平滑化は、
**議員側とユーザー側の両方に同じものを掛ける**。片方だけだと
`agree = 1 - |u.score - p.score| / 2` が意味を失う。
詳細は `docs/implementing-match-api.md`。

## 5. Cloudflare のサービス割り当て

| 用途 | サービス |
|---|---|
| フロント（記事一覧・詳細・ユーザーページ） | Pages |
| A のバッチ / B・C の API | Workers |
| utterances、answers、記事、議員マスタ | D1 `civic-compass-db`（バインディング `DB`） |
| 議員プロファイル、セル逆引き、ユーザープロファイル | KV（バインディング `PROFILES`） |
| 発言原文・スクレイプ結果 | R2 |
| segment 分割・フレーム抽出 | Workers AI or AI Gateway 経由の外部 LLM |
| LLM 呼び出しのキャッシュ・レート制限・ログ | AI Gateway |
| 夜間の差分取り込み | Workers Cron Triggers |
| 意見投稿の荒らし対策 | Turnstile |
| API キー | Secrets Store |

**API は基本的に KV だけを読む。** D1 はプロファイルを作り直すときの元データ。
KV のキー設計は `docs/data-reference.md`。

**AI Gateway のキャッシュは必ず入れる**（デモ中のレート制限事故を防ぐ）。

Vectorize は現時点では不要。

## 6. 割り切りと注意

### スコープ

- 全国会議員は無理。**15人**に絞る（`scripts/kokkai/politicians.json` が正）
- 発言は**直近3〜4年**のみ。10年前の発言を「あなたと似ています」と出すと
  現在の立場と食い違う。ただし首相・閣僚経験者は在職前まで window を広げる
- プロファイルが未整備の議員は**候補から除外するフラグ**を持つ
  （揃っていない議員が常に低スコアで出るのを防ぐ）

### 正規化

議員は数百発言、ユーザーは十数件。**生の件数ではなく必ず `share`（比率）で比較する。**

### 中立性（審査で必ず聞かれる）

- 「参考情報であり投票の推奨ではありません」を明示
- 必ず出典 URL を併記
- 上位だけでなく「考えが遠い議員」も見られるようにする
- ラベル（保守／リベラル／左右）で断定表示しない。**軸ごとの記述文で見せる**

`target` を「強い立場／弱い立場」に分類する案があるが、この線引き自体が
価値判断を含む。**分類はマッチ計算の内部でのみ使い、UI に出さないこと。**

### 著作権

国会会議録の発言は公文書なので原文を引用できる（`quotable: true`）。
議員個人サイトの文章は著作物なので**要約に留めてリンクを張る**
（`quotable: false`。`docs/data-reference.md`「公式サイト由来は原文を出さない」）。

国会会議録 API への短時間大量アクセスは禁止されているのでクロール間隔に注意。

### 政党の流動性

`party_at_time`（発言時点の党籍）が必須。現所属で集計すると事実として誤り。
いのちの党の発言はすべて「れいわ新選組」名義、中道改革連合の議員の発言も
大半が旧立憲・旧公明時代のものになっている。

この流動性は弱点ではなく、**政治家個人の思想でマッチさせる設計の正当化**に使える。
